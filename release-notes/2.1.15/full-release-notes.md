# Bisq 2.1.15 Release Notes

Proposed release notes for the `release-candidate-2.1.15` branch. This release changes how Bisq starts and isolates Tor, adds support for external Tor and bridges, extends the API for mobile clients, and tightens network and build checks.

## Scope

These notes describe the net changes from `v2.1.14` (`945dec0ecb3d4f750060047078037afdc437f070`) to `release-candidate-2.1.15` at `890386ab407fedda22a69089a39b11c4b4bb3066`. The Tor library submodule is pinned at `6edc00e7413a1a95767586abc4899a8f0202ac85`. The checkout declares version `2.1.15` in `gradle.properties`. These are release-candidate notes, not a claim that version 2.1.15 has been published. Changes were checked against the resulting code, configuration and specifications; the range also contains the extraction of the Tor library into a Git submodule, so the parent repository's file diff alone does not describe the Tor changes.

## Upgrade and Operator Notes

- **Bundled Tor on Linux:** Bisq now runs the Tor expert bundle included in the build on Linux, macOS and Windows. Linux packages no longer require the distribution's `tor` package. An existing system Tor installation and service are not removed by the update; Bisq does not use them for its own Tor start. The bundled Tor is from Tor Browser 16.0, with Tor daemon 0.4.9.15. Linux still needs the system's glibc and `libz.so.1`.
- **Tor sandbox:** Bisq enables the sandy sandbox for the Tor it starts. The build takes sandy 1.0.0, the first public release of sandy, from its GitHub release. If the system cannot enforce any supported sandbox level, or the configuration asks for an operation the sandbox cannot allow, Tor startup fails instead of silently starting without the sandbox. Set `application.network.configByTransportType.tor.sandbox.enabled=false` only when the operator accepts running Tor without it. External Tor, including Whonix, is outside this sandbox. Sandbox strength can vary with the operating system and the configured bridges.
- **Bridges and pluggable transports:** `bisq.conf` can select a built-in bridge type with `builtInBridges` or supply complete custom `bridges` lines, but not both. Bisq uses the matching transport programs from its Tor bundle. Bridges that need a pluggable transport require `sandbox.allowPluggableTransports=true` while the sandbox is enabled. The desktop network settings have a switch for that permission, which applies after a restart; bridge selection itself is configured in `bisq.conf`. Windows cannot run pluggable transports inside the sandbox. Use bridges without them or explicitly turn the sandbox off on Windows. A configured bridge that cannot run fails the start; Bisq does not fall back to a direct connection.
- **Torrc overrides that run code:** The torrc overrides `ClientTransportPlugin`, `ServerTransportPlugin`, `AccelName` and `AccelDir` make Tor start a program or load a library. If `bisq.conf` assigns one of them, also through a substitution or an include, the start of Bisq's own Tor fails with an error. The error names the override and the JVM option that gives it instead. Program arguments and JVM options can still set these overrides. With bridges, Bisq ignores `ClientTransportPlugin` overrides, so they do not stop the start. The reason: Bisq writes `bisq.conf` itself, and whoever can change that file could otherwise make the next Tor start run code. External Tor gets no torrc overrides and is not affected.
- **Torrc override values:** An override value without quotes, such as `AvoidDiskWrites = 1`, now reaches Tor as its text. Tor accepts only `0` and `1` for its boolean options, so a value of `true` stops the start of Tor with Tor's error. A list as an override value fails while reading the configuration.
- **Existing Tor data:** At the first start, Bisq moves the old Tor state into the new `tor/data` layout. Tor binaries are installed in `tor/bin`; sandy has its own directory. Backups omit the Tor state, bundled binaries and sandy because Bisq can recreate them. Backups also omit `tor/data-mode`, which records whether a sandboxed Tor wrote `tor/data`; restored next to another Tor data directory, it would describe the wrong directory. A backup retains `external_tor.config`, which can contain an external Tor control password in plain text. Handle and share backups accordingly.
- **External Tor:** Bisq can use external Tor on Whonix, when `TOR_SKIP_LAUNCH` is set, or when its configuration selects external Tor. The configuration file `external_tor.config` supplies its control endpoint and authentication. Cookie authentication uses SAFECOOKIE. External Tor must offer SOCKS username/password authentication and must not disable `IsolateSOCKSAuth` on the port Bisq uses. Bisq refuses a reported `NoIsolateSOCKSAuth` setting; it cannot verify a filtered configuration such as onion-grater on Whonix. An external Tor on another host must be reached over a trusted network because the control connection carries onion-service private keys.
- **Failed headless starts:** Seed nodes, oracle nodes and the API application exit with status 1 when application startup fails. A service manager with `Restart=on-failure`, or a container runtime with a restart policy such as `restart: on-failure`, then restarts them. The API application also exits when its API is enabled but its HTTP server does not run, for example because another process uses the port or the TLS context cannot be created. A cause that stays leads to a restart loop, and every restart starts Tor and connects to the seed nodes again. Startup also fails when it takes more than 5 minutes, which a slow Tor start with bridges can exceed. Operators should inspect the cause before allowing repeated retries. The node monitor still only logs an initialization failure.
- **Shutdown after Tor failures:** If Tor processes still run after the Tor library stopped them forcibly, the shutdown of the Tor service fails and names those processes. The applications log the failure and still shut down the services that follow the network.
- **API Docker image:** Pass `--build-arg BUILD_COMMIT=$(git rev-parse HEAD)` when building the API image. The Docker build context leaves out `.git`, so without this argument the node reports its commit hash as `unknown`.

The exact configuration, migration, sandbox refusal and compatibility rules are in the [Tor startup specification](../../docs/specifications/network/tor-startup.md). The [build guide](../../docs/dev/build.md) shows `bisq.conf` examples and the data directory.

## Notable Changes

### Tor startup, privacy and desktop controls

- Bisq chooses the control and SOCKS ports of its own Tor, authenticates to its control port, and checks after bootstrap that the SOCKS port belongs to that start. Configuration cannot replace Tor's protected listeners or authentication. Its Tor log is written to `tor/tor-stdout.log`, rotated before another start at 10 MiB, and available from the desktop resources page. The log zip omits the home-directory path. Tor's own notices may still disclose private bridge details; review a log zip before sharing it.
- Tor startup and shutdown now coordinate concurrent callers. A failed start can be retried, and a shutdown waits until no Tor of that service runs. The shutdown also stops and waits for the processes below the Tor process, such as the programs of pluggable transports. Processes that a shutdown could not stop stay tracked: the next start stops them first, and a later shutdown reports them. If the cleanup after a failed start fails as well, the error still shows the cause of the failed start.
- Bootstrap warnings in the Bisq log no longer name the relay or bridge that Tor could not reach. Sandbox refusal messages explain the reason and possible configuration changes. On the desktop, the notice about a weaker sandbox level identifies the missing protection; the user can dismiss each distinct set of weaknesses. Network information shows the running Tor version.
- The network settings switch writes only `sandbox.allowPluggableTransports` into `bisq.conf` and asks for confirmation before enabling it. It is unavailable while the sandbox is off and on Windows. Bridge selection remains a separate configuration step.
- Tor now has a separate repository and a pinned Git submodule. The parent build and packaging use that pinned library. Builders need to initialize the submodule before building.

### API for mobile clients

These changes come from the `for-mobile-based-on-2.1.14` branch.

- `GET /api/v1/info` returns the node version, the image version on containerized distributions, and the supported API features. It needs the `SETTINGS` permission, because the image version names the Docker build. `GET /settings/version` stays for clients that already use it.
- `GET /api/v1/trades/{tradeId}/account-data-banned` tells a buyer whether the seller's payment account data matches data that the security manager banned. The check is read-only. Reporting the seller, cancelling the trade and blocking the payment confirmation are left to the client. A `false` result is not final, so a client should check again right before the buyer confirms the payment. The feature key is `banned-account-data`.
- The offerbook API (`OFFERS`, `NUM_OFFERS` and the REST offer list) now shows the same offers as the desktop offerbook: an offer of another maker is hidden when its maker is banned or ignored, its amounts cannot be converted at the current price, or the seller lacks reputation for its amount. Own offers are always shown, so that the app can warn its user. Each item has the new field `hasSellerSufficientReputation`. The field is advisory, because the node checks the reputation again when an offer is taken. `NUM_OFFERS` counts the same offers that `OFFERS` sends. A change of a price, a reputation, the ban list or the ignore list updates the visibility at most every 30 seconds.
- The API deletes the pairing QR code file at start and at shutdown, so a file on disk always belongs to the running process. A failed TLS setup now stops the HTTP server and reports the error.
- Cancelling a trade through the API writes "cancelled the trade" into the trade log instead of "rejected the trade". The API no longer blocks while the trade log message is sent.

The rules for the offerbook API are in the [offerbook API specification](../../docs/specifications/api/offerbook.md).

### Network and application reliability

- HTTP response bodies are bounded after decoding. An oversized or endless response fails the request and discards the connection. Tor HTTP responses also have a bounded status line and headers; malicious responses cannot consume unbounded response-head memory. Failures of one transport are logged without obscuring another transport's failure.
- The Tor HTTP client and HTTP request service close their resources during shutdown. The API waits until the Tor transport is ready before publishing its onion service and binds the API server to the address that Tor or the sandbox relay can reach.
- Bisq avoids filesystem deletion through symbolic links and Windows junctions. Tor data migration and cleanup remove the link itself rather than its target. Random network ports use the complete usable range from 1 to 65535.
- Network stores now start removing expired entries when the network services start, after the stored data has been read, and stop at shutdown. Before, the removal started when the storage was created. Decoded public keys are shared between network entries with the same key, which reduces memory use. The fields that are excluded from hashes are resolved once per class.
- The banned account data set is safe for concurrent access by the alert service, the UI and the API. Deleting a directory tree no longer stops at a dangling Windows junction; Bisq deletes the junction itself.
- A proof-of-work string is bounded, preventing an attacker-controlled value from producing unbounded log or display text. The Windows OS check no longer mistakes Darwin for Windows. The external-Tor indicator refreshes when the Tor transport finishes starting.

### Build and verification

- The build moves to Gradle 9 and JDK 21.0.13. The release JDK, Docker image, CI jobs and JavaFX version are pinned consistently. CI builds on Linux, Intel and Apple Silicon macOS, and Windows; its Tor step prints diagnostics when a test times out.
- The build check of `check` accepts every build of the pinned Java update 21.0.13, because Azul builds one update more than once and an installer may offer only the latest build. A release build still needs the exact pinned JDK build, because the installers bundle the build JDK as their runtime.
- Tor bundles and the sandy binaries are verified against pinned hashes and their signing rules. The build resolves the sandy 1.0.0 archive of each platform as a dependency. It checks the archive against its pinned SHA-256 value and against the `SHA256SUMS` file of the release, which must carry a signature by the pinned sandy release key. The build refuses malformed or untrusted key material and checks signature validity at signing time. Installer generation fails when `jpackage` fails, times out, or produces no package. Linux installer builds need the package tools listed in the build guide.
- `publishAll` publishes all modules in one build, so `-P` and `-D` options reach every publication, and every internal dependency in the POM files has a version. JitPack builds work again. The build commit hash is reproducible and no longer part of the classes of `common`. Builds without Git, such as the API Docker build, can pass it with `-PbuildCommit`.
- The verification metadata may contain only one `key-servers` element, and the key export no longer rewrites the metadata.
- CI includes a nightly check against the previous release. Dependency verification and toolchain selection have been updated for the extracted Tor build. Tests cover Tor startup, sandbox configuration, backup behavior, HTTP bounds, Windows OS detection, and application startup failures.
