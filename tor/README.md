# Tor build

The Tor build contains the Tor integration of Bisq:

- `tor`: starts, controls and connects to Tor, and publishes onion services (`TorService`).
- `tor-common`: the torrc generation and the copies of Bisq utilities which the Tor build uses.
- `jsocks`, `jtorctl`: copies of the SOCKS library and of the Tor control protocol library. See their READMEs.
- `tor-local-network`: a tool which starts a private Tor network for tests.
- `tor-platform`: the dependency constraints of the Tor build.

## No dependencies on other Bisq modules

The Tor build does not depend on other Bisq modules or on the `build-logic` build of Bisq. Do not add such a
dependency.

- `build-logic` contains the Gradle plugins of the Tor build. `tor-binary` and `gradle-tasks` exist only here. The
  other plugins are unchanged copies of plugins in the `build-logic` of Bisq and keep their plugin IDs.
- The classes in the packages `bisq.network.tor.common.*`, except `torrc`, are copies of classes of `bisq.common`.
  A copy keeps the sub-package and the class name: `bisq.common.util.StringUtils` becomes
  `bisq.network.tor.common.util.StringUtils`. A copy only contains the members which the Tor build uses. A change of
  an original does not change its copy. A copy never uses the package of the original, because two classes with the
  same name on one class path break the Android build of bisq-mobile and make the JVM load whichever comes first.
- `PlatformServices` declares the operations which depend on the platform of the host application: the own process
  ID, the commands of the running processes, and whether the Tor build may set POSIX file permissions. The host passes
  an implementation to `TorService`. Bisq passes `BisqTorPlatformServices` of the network module, which uses
  `FacadeProvider` and `FileMutatorUtils` of `bisq.common`. bisq-mobile calls `FileMutatorUtils.setup(false, false)`,
  so the Tor build sets no POSIX permissions there.
- The API of the Tor build only uses types of the Tor build. `TorTransportService` of the network module adapts the
  types of Bisq: it passes the `TorKeyPair` of Bisq as `OnionServiceKey`, and its `Config` implements
  `TransportConfig` of Bisq and wraps `TorTransportConfig`.

## Android

The node app of bisq-mobile runs `TorService` with an external Tor on Android, from API level 33. Code which runs in
this mode must only use Java APIs which Android 13 provides. This is `TorService.initialize` up to the connection to the
external Tor, `TorController`, `TorControlProtocol` and `FileUtils`. If the connection fails, `TorService` starts the
installer, which fails on Android because the app has no `tor.zip`. For example, `java.util.HexFormat` needs API level
34, and `ProcessHandle` does not exist on Android. The Tor build uses Guava instead of `HexFormat`. The embedded Tor
process and `tor-local-network` only run on desktop systems.

## Build

The Tor build still uses these files of the Bisq repository: the Gradle wrapper, `gradle/libs.versions.toml`, the root
`gradle.properties` (`version` and `tor.version`) and the dependency verification in `gradle/`.

Run these commands from the repository root:

- `./gradlew -p tor build` builds the Tor build alone.
- `./gradlew :tor:tor:test` runs the tests of `tor` in the composite build of Bisq.
- `./gradlew :tor:tor:verifyTorBinary` downloads and verifies the Tor expert bundle. See
  [build-logic/tor-binary/README.md](build-logic/tor-binary/README.md).

`tor.zip` and `TorBuildVersion` are generated by Gradle tasks. An IDE build which does not run Gradle tasks needs one
Gradle build of `tor` first.
